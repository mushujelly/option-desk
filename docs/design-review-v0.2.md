# Option Desk v0.2 设计评审意见

- 评审对象：`docs/infrastructure-design.md` v0.2
- 日期：2026-09-26
- 状态：评审意见，不直接修改设计文档；是否采纳由设计作者决定

## 总体评价

v0.2 按用户要求收敛为“发生时基准（冻结）+ 当前状态（覆盖）”两份快照，移除了连续行情历史、定时/收盘快照与任意时点回放。方向正确，且顺带消除了 v0.1 评审中最担心的存储规模问题：现在存储规模约为“事件合约数份基准 + 监控合约数份当前状态”，不随刷新次数增长，分区、归档等运维负担基本消失。

v0.1 评审建议跟进状态：

- 已解决：时间序列表分区 / 最新视图实现（被两份快照收敛带走）。
- 仍然适用：请求预算一等设计、附录 DDL 草稿（按 `event_baselines` / `current_states` / `context_cache` 新表写）、keyset 分页、SLI 阈值、交易所日历点名库、原始报文归档命名规范。

## P0：发生时行情的可获得性（阶段 0 门禁）

`event_time_verified` 是两份快照模型的基石，但存在现实时序矛盾：Discord 消息按 30–60 秒轮询 + 解析，事件时点在捕获发生时行情时往往已经过去。

建议：

1. 把第 20 节第 11 项升级为阶段 0 的通过门禁：在写任何采集代码前，先验证 Schwab / OpenD / Polygon 是否支持按事件时点返回期权历史报价，以及支持的粒度（分钟级？tick 级？）。
2. 验证结论出来后，再把“可接受时间偏差”写成具体配置值（如 ±30s / ±60s），而不是停留在“规定偏差范围”。
3. 若三家均不支持事件时点历史报价，大部分基准将只能是 `first_observed`，对照功能会系统性降级——这个降级形态要在设计里提前写明，而不是等联调才发现。

## P1：对照接口做成单次原子读取

第 16 节要求“一次对照读取同一个当前版本，避免指标与输入错位”。建议直接落在 API 设计上：提供一个对照接口，单次请求返回 `baseline + current + version`，而不是两个独立接口由前端拼接。否则版本机制只存在于文档里，前端仍可能读出撕裂数据。

## P1：`provider_mismatch` 时对照页不能是空的

第 10.2 节规定基线与当前 provider 不同时默认不计算行情差值，约束本身正确。但需明确 UI 形态：建议并排展示两份行情包 + 显眼的跨源提示，仅差值列显示“不可比”。否则核心功能在这些单子上直接消失，用户会误判为 bug。

## P1：共享 current_state 的档位冲突

第 14.1 节规定相同合约的多笔事件共用一份当前状态，但 `watchlists` 有刷新档位。同一合约出现在两个不同档位的关注列表时，实际刷新频率取谁？建议定一条显式规则（如取最高档位），否则实现时会各写各的。

## P2：“回填”在新模型下需要重新定义

第 13.1 节与第 16 节 API 中仍保留“回填”，但新模型下已无行情历史可回。建议一句话定义：回填 = 为新增监控合约补齐当前状态 / 为缺失基准的手工重抓（带审计日志）。避免阶段 1 做任务系统的人按旧理解实现。

## P2：基线复制背景输入的边界

第 14.3 节要求“基准需要的背景、链级计算输入或充分统计量复制进基准”，但：

1. 链级输入可能很大（整条链的统计量），需明确只复制哪些字段（建议：同到期链统计 + 样本数 + 时间戳）。
2. 事件时点的链数据同样面临“事后抓不到”的问题，需明确 fallback：用就近快照 + 显式时间戳，还是直接标不可用。

## P2：给冻结留一个带审计的手工重抓入口

第 14.2 节规定“基准完成一次捕获尝试后冻结”，防漂移是对的。但现实中存在“当时没抓到、事后数据源补了数据”的情况。建议在数据管理页保留一个手工重抓入口（写审计日志、不自动触发），比“永远冻结”更实用。
